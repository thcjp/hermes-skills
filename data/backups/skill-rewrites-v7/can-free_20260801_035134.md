# CAN — Clock Address Naming（免费版）

CAN免费版是一款基于Clock Address Naming（CAN）协议的内容寻址工具，它通过独特的时间戳、内容哈希和可读名称的三列记录方式，为用户提供了一种高效、可靠的内容管理解决方案。

## 解决的三个问题

CAN免费版旨在解决以下三个常见问题：

1. **内容验证**：如何确保内容在存储和传输过程中未被篡改？
2. **内容检索**：如何快速定位特定内容？
3. **内容管理**：如何有效管理大量内容？

## 一行三列的修复方案

每条事件记录包含以下三列信息：

- WHEN：Unix时间戳，记录事件发生的时间。
- WHERE：内容的SHA256哈希值，确保内容的唯一性和不可篡改性。
- WHAT：可读名称，便于搜索和识别内容。

## 核心能力

### 三列协议记录

CAN免费版通过三列协议记录事件，每条记录包含WHEN、WHERE和WHAT信息。

- WHEN：Unix时间戳（毫秒），确保时间戳不为0且不指向未来。
- WHERE：内容的SHA256哈希值，用于唯一标识内容。
- WHAT：人类可读的名称或标签，便于搜索和识别内容。

### 内容哈希校验

对内容进行SHA256哈希计算，以确保内容的唯一性和不可篡改性。

### 本地append-only日志

支持本地append-only日志，确保数据的安全性和不可篡改性。

### 三问自评估

通过WHEN、WHERE、WHAT三列记录，自动进行自评估，验证记录的有效性。

## 错误处理

| 错误场景 | 原因 | 处理方式 |
|---:|---:|---:|
| `when`为0或负数 | 时间戳未初始化 | 重新取当前Unix毫秒，须 > 0且 ≤ 当前时间 |
| `where`非十六进制 | 哈希计算失败 | 重新对原始字节计算 `sha256`，确认编码一致 |
| `what`为空字符串 | 未命名事件 | 赋予至少一个可搜索标签 |
| 哈希不匹配日志 | 内容被改动 | 免费版需手动比对；付费版自动告警 |
| 日志文件被锁定 | 并发写入冲突 | 采用append-only追加模式，必要时加文件锁 |

## 常见问题

### Q1：CAN与区块链有何区别？
CAN不是区块链：无共识、无全局状态、无代币。它只是本地append-only三列日志，本质是索引。

### Q2：必须用 `xc.cx` 端点吗？
免费版以三问自评估为主。付费版提供端点校验与公共日志查阅。

### Q3：NOT算失败吗？
不算。NOT是数据，表示某项缺失。记录NOT比只记录成功更诚实。

### Q4：免费版能用于MCP工具响应吗？
能记录，但跨管道编码规范化为付费版专享，免费版需手动确保编码一致。

### Q5：如何升级到付费版？
参考 `can` 付费版SKILL.md，解锁评估端点、篡改告警、并行索引、OTS同步等能力。

## 已知限制

- 依赖本机时钟：`WHEN` 准确性受系统时钟影响。
- 不提供全局共识：日志是本地的。
- 哈希计算需手动规范编码：同一内容不同编码产生不同 `sha256`。
- 不提供评估端点校验：免费版仅靠三问自评估。
- 不提供篡改自动告警：需手动比对哈希。

## 1. 三列协议记录的详细说明

为了更清晰地说明三列协议记录的细节，以下是对每个字段的详细解释：

- `when`：记录事件的Unix时间戳（毫秒），确保时间戳不为0且不指向未来，以保证日志的准确性和顺序性。
- `where`：内容的SHA256哈希值，用于唯一标识内容，不依赖于文件系统结构，提高内容的安全性。
- `what`：人类可读的名称或标签，便于搜索和识别内容，同时提供额外的元数据信息。

### 字段示例

```
1742428800000,a7f3b2c1d4e5,test-entry
```

这里，`1742428800000` 是事件发生的时间戳，`a7f3b2c1d4e5` 是内容的SHA256哈希值，`test-entry` 是该事件的可读名称。

## 2. 内容哈希校验的精确性

为了确保内容哈希校验的精确性，以下要点需要特别注意：

- 使用SHA256算法进行哈希计算，以确保内容的唯一性和不可篡改性。
- 确保输入内容的编码一致性，避免由于编码差异导致的哈希值不同。
- 在记录哈希值时，应记录完整的哈希值，而非片段，以提高安全性。

### 校验步骤

1. 对待校验的内容进行SHA256哈希计算。
2. 将计算得到的哈希值与记录的哈希值进行比对。
3. 如果哈希值匹配，则内容未被篡改；如果不匹配，则内容可能已被篡改。

## 3. 本地append-only日志的维护

为了保证本地append-only日志的维护，以下要点需要遵循：

- 日志文件应采用追加模式写入，确保日志的完整性。
- 避免对日志文件进行修改或删除操作，以保持日志的不可篡改性。
- 定期检查日志文件的完整性，确保没有损坏或丢失。

### 维护步骤

1. 使用追加模式写入日志文件。
2. 定期备份日志文件。
3. 使用校验算法（如CRC32）检查日志文件的完整性。

## 4. 三问自评估的执行细节

为了详细说明三问自评估的执行细节，以下是对每个问题的具体执行步骤：

- **WHEN**：检查是否有Unix时间戳，确保时间戳不为0且不指向未来。
- **WHERE**：检查是否有内容哈希，确保哈希值是有效的SHA256哈希。
- **WHAT**：检查是否有可读名称，确保名称是非空字符串。

### 自评估示例

```
WHEN: 有时间戳，符合要求。
WHERE: 有内容哈希，符合要求。
WHAT: 有可读名称，符合要求。
```

如果所有问题都得到肯定回答，则自评估结果为“CAN”，表示内容寻址成功。如果任何一个问题没有得到肯定回答，则自评估结果为“NOT”，表示内容寻址失败。
